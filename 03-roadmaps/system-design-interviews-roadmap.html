System Design Interviews Roadmap

System Design Interviews Roadmap

New

Jun 21, 20264 min read

System design interviews are not asking whether you memorized a shopping list of components. They are asking whether you can take an ambiguous product requirement, make the hidden constraints explicit, and choose trade-offs under time pressure.

This roadmap is the interview lens over the same foundations: how to structure an answer, how to justify each component, and how to avoid overbuilding before the problem demands it. Later, concrete use cases like rate limiter, URL shortener, news feed, chat, and metrics/logging can plug into this page as practice problems.

Interview answer shape

Use this structure for almost every design:

  1. Clarify the product behavior — What are users doing? What is explicitly out of scope?
  2. Estimate the load — Requests, writes, reads, storage, fan-out, latency target.
  3. Define the API — What contract does the system expose?
  4. Pick the data model — What is the source of truth? What must be indexed?
  5. Choose the architecture — Stateless services, storage, cache, queue, async workers.
  6. Handle scale and failure — Partitioning, replication, retries, idempotency, observability.
  7. Call out trade-offs — Why this design, and what would change at 10x?

Read in order

1. The interface and request path

  1. API Design — The first thing interviewers can evaluate: naming, versioning, idempotency, pagination, and error shape.
  2. 3 — The wire-level request behavior behind API latency, multiplexing, and connection reuse.
  3. TLS 1.3 and mTLS — The identity and encryption layer behind HTTPS, gRPC, service-to-service calls, and zero-trust designs.
  4. API Gateway — Auth, rate limiting, routing, and observability at the edge.
  5. GraphQL — A useful answer for client-driven aggregation problems, not a default.
  6. API Protocols Compared — REST, gRPC, GraphQL, WebSockets, SSE, and long-polling as workload-specific choices.
  7. gRPC vs REST — The style trade-off once latency, payload size, streaming, or service-to-service traffic matters.

2. Storage and consistency

  1. Database Concepts — Storage engines, indexes, WAL, and why the storage choice drives the rest of the design.
  2. CAP and PACELC — How to explain consistency trade-offs without reciting a slogan.
  3. Isolation Levels — What correctness guarantee your database actually provides.
  4. MVCC — Snapshot reads, write conflicts, and why “read-heavy” is not a free category.

3. Performance and scale

  1. Caching Techniques — The most common interview optimization, and the fastest way to introduce stale reads.
  2. Consistent Hashing — The partitioning answer behind distributed caches and key-value stores.
  3. Load Balancers — The request-distribution layer behind most scalable designs and many real outage stories.
  4. DNS, GeoDNS, and Anycast — Global routing, failover, and edge selection before traffic reaches your system.
  5. DynamoDB — A concrete cloud key-value design that packages many interview primitives together.
  6. Redis — Cache, counter, queue, rate limiter, lock manager if you are careful — footgun if you are not.

4. Async systems and workflows

  1. Kafka — Logs, partitions, consumer groups, backpressure, and when async turns a request path into a pipeline.
  2. Event Sourcing & CQRS — When the history is the data model.
  3. Change Data Capture — Moving changes through the system without dual writes.
  4. Choreography vs Orchestration — Who owns the workflow when multiple services participate?

5. Production-quality answers

  1. Fan-Out Strategies — The read/write trade-off behind feeds, notifications, and social products.
  2. Backend for Frontend — When one API per client is clarity, and when it is just another service.
  3. Multi-Tenancy — The cost model behind B2B SaaS design.
  4. Observability — The difference between a whiteboard design and a system someone can operate.
